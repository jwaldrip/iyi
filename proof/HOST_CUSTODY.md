# Host custody contract

## Status and threat boundary

This is a static contract, not a qualified launcher or a grant to run one. The existing E3 and strict-origin refusals remain in force. The workload, cage, compiler-output inode, commands, image and capability ceiling do not change. The preflight reports observations or unavailability with provenance; it does not authenticate them, establish eligibility or authorize execution. It attempts no load, attachment or execution-identity test.

The adversary includes the workload and any host user whose arbitrary code is in scope. A separate observer UID and root-owned storage do not protect against a hostile host user with sudo or equivalent Docker control. GitHub-hosted Linux's default runner user has passwordless sudo. If that user may run hostile code with that authority, no local root boundary described here qualifies. A separately administered execution and collection trust domain is needed. An assertion that the runner user is not hostile requires an actual threat-boundary decision; a fixture's assertion is not that decision.

The protected snapshot and independent terminal accounting are theoretical options to qualify, not proof of workload custody. Sealed memfd bytes are optional immutable tool storage. They do not establish a launcher, independent terminal status, original-output custody, or an authenticated approval.

## Required trust chain

1. An independently controlled, authenticated channel binds an actual reviewer and approved subject to the exact workflow, checkout, run, attempt, observer executable, BPF object, execution dependencies, recipe, execution configuration and invocation. A manifest generated or signed solely by the untrusted build cannot authorize itself. No authentication mechanism is specified or implemented here; an unavailable channel is a refusal, not permission to invent a key.
2. A trusted bootstrap precedes any candidate compiler, workload, untrusted test or build hook on the runtime host. Build and runtime jobs are separate. Repository code, including scripts, importers, build tools and verifiers, never runs as root. A future privileged bootstrap uses independently reviewed system utilities and fixed operations, not a root repository-code entry point.
3. Source bytes are untrusted and bounded. Staging must avoid attacker-selected path traversal, symlinks, devices and FIFOs. Create fresh destination inodes in root-private storage; never adopt an attacker-controlled inode by changing its owner. Keep unverified bytes private and out of evidence exports. Read back and authenticate each destination against the approved digest after copying, then expose only the approved copies read-only. Protect executable, dependencies, loader, recipe, configuration and paths from the adversary for the full execution, including any pathname fallback.
4. A proposed system service launches an absolute protected native ELF under an actual nonroot observer UID distinct from the workload and collector. No shell wrapper, privilege prefix, `PIDFile=`, ignored failure or success-status remapping. The observer has no sudo, Docker group/socket, writable code directory or payload descriptor inheritance. Verify actual nonroot identities, empty supplementary groups and exact capability state at BPF use; service configuration alone is not proof. Do not assume `PrivateUsers=yes` preserves the required host capability domain. The exact service and collector remain unimplemented and require separate review and authorization.
5. PID 1's retained system-service accounting, read directly by a protected independent collector, must bind boot ID, unique unit, invocation ID, cgroup, execution configuration, main PID, monotonic start and exit times, `ExecMainCode`, `ExecMainStatus` and `Result`. Reject missing, reused, restarted, reset, ambiguous, signaled, timed-out, OOM or nonzero outcomes. Collect complete diagnostics separately and read back the exported protected output. Neither observer text nor journal message bodies are independent terminal authority. A Docker CLI service exit is not the container workload's raw wait status.
6. The collector and export must be outside the workload and observer's write authority. Authentication of the collected record and independent validation of the approved digest and output readback are prerequisites, not booleans supplied by the producer. Independently review the bootstrap, service, collector, credential and descriptor boundaries, evidence export and failure cases before any hosted qualification. Runtime authorization is separate from that review and does not authorize strict execution.

Even an authentic observer exit and protected observer bytes do not prove the original compiler output. Strict origin still needs independently correlated original output and reference objects, successful execution and synchronous stop, protected byte sampling under writer exclusion, task generation, namespaces, mounts, cgroup, descendants, teardown and exact source-slot attribution. Do not widen capabilities or alter the cage to make this route work.

## Offline data contract

`host_custody_contract.assess(expected, inventory, protected_copy, terminal)` examines only bounded, plain in-memory dictionaries. It has no I/O, subprocess, cryptographic verification or access to an authority. Its exact field sets are defined in the function. Unknown, extra, absent, wrongly typed, oversized or contradictory data is refused. Digests are lowercase SHA-256 strings, not verification of bytes. The `authority` and `reviewer` values are untrusted identifiers, not attestations. The diagnostic digest in the expected fixture is an asserted binding, not a preapproval mechanism for unknown runtime output.

`REFUSED` means the supplied records are invalid or inconsistent. `CONSISTENT_UNATTESTED` means only that their claims agree under this model. Both have `runtime_admission`, `authority_verified`, `user_authorization_verified` and `terminal_independently_attested` fixed false. A fabricated internally consistent PID 1 record can reach only the latter, never a green, authorization or admission. The contract cannot detect a matching replay when all claimed identities are forged together; that requires an independently authenticated authority and collector bound to the actual run. Consumers must not convert either status into an operational gate or production claim.

A future collector must independently obtain and authenticate exact identities, approved artifact digests, execution configuration, terminal status and protected output readback. It must also establish the threat-domain separation and user authorization outside these records. No current implementation provides those guarantees.
